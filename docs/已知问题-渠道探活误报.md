# 已知问题：渠道探活误报（火山方舟套餐）

**记录日期：** 2026-08-29  
**状态：** 已确认，暂不修复  
**影响范围：** 使用不支持 `GET /models` 的 OpenAI 兼容上游渠道

## 现象

渠道管理中的“探活”将“火山200”标记为异常；但该渠道实际绑定的模型可以正常完成对话调用。

## 已验证结果

| 项目 | 结果 |
| --- | --- |
| 渠道 | 火山200（`channel_id=112`） |
| 渠道状态 | 启用（`status=0`） |
| 配置的探活地址 | `https://ark.cn-beijing.volces.com/api/plan/v3/models` |
| 当前探活结果 | `GET /models` 返回 `404` |
| 实际推理验证 | 使用已绑定的 `deepseek-v4-flash` 请求 `POST /api/plan/v3/chat/completions` 返回 `200` |

因此，该渠道本身、密钥和模型供应绑定均正常；“异常”是健康检查误报。

## 根因

当前 `AiChannelServiceImpl#doProbe` 使用统一的 HTTP `GET` 请求访问
`baseUrl + healthCheckUri`，未配置路径时默认 `/models`，并且只将 HTTP 2xx 视为健康。

火山方舟套餐地址 `.../api/plan/v3` 不提供该模型列表端点，因此返回 404。与此同时，运行时模型调用会按版本化 base URL 正确拼出 `/chat/completions`，所以真实推理正常。

相关代码：

- `ruoyi-system/src/main/java/com/ruoyi/system/service/impl/AiChannelServiceImpl.java`
- `ruoyi-system/src/main/java/com/ruoyi/system/ai/OpenAiCompatibleEndpoint.java`

## 当前影响

- 手动探活与定时探活会持续累计失败次数，并最终显示为“异常”。
- 健康状态当前仅为监控信号，不会直接阻止模型路由；因此不影响该渠道的正常对话调用。
- 监控统计与渠道管理页面会出现错误告警，容易误导运维判断。

## 后续统一改造建议

健康检查应统一定义为“最小真实模型调用”，而不是依赖模型列表接口：

1. 从该渠道的启用模型供应中选择一个探测模型，优先选择权重最高的供应。
2. 复用运行期的协议适配、端点拼接与鉴权逻辑，避免探活与实际调用走出不同地址。
3. 使用非流式最小请求，例如 `max_tokens=1`，以验证鉴权、模型标识和推理端点。
4. 按渠道协议实现请求构造策略（OpenAI 兼容、Anthropic、Gemini 等），但统一返回健康检查结果与状态回写逻辑。
5. 没有启用模型供应时应标记为“未配置/未知”，而非判定上游不可用。

改造时需要补充单元测试，至少覆盖：版本化 base URL、`GET /models` 不可用但对话成功、无可用模型供应、认证失败与超时等场景。
