# 会话身份与访问控制

> 本文说明 `sessionId` 的产生、流转与鉴权模型，记录 2026-08-10 这轮安全加固的内容，
> 并给出后续演进路线与**新增接口必须遵守的规约**。
>
> 涉及会话、工作区、上下文文件、事件订阅的改动，动手前请先读第四节。

---

## 一、现状:会话身份是怎么设计的

### 1.1 sessionId 由客户端生成

新对话的 `sessionId` 是**前端生成**的 UUIDv4(`ruoyi-ui/src/views/ai/chat/composables/useSessions.js` 的 `genId()`),
不是后端分配的。定时任务触发的会话则由服务端生成(`AiJobDispatcher.newSessionId()`,32 位无连字符 UUID)。

这不是随手为之,它换来三件在「首轮发送之前」就必须成立的能力:

| 能力 | 为什么需要 id 先存在 |
| --- | --- |
| 事件预订阅 | 新标签页要在首轮发送前挂上 `chat.session.subscribe`，否则多端同步要等第一轮跑完 |
| 先传附件再提问 | 「新开对话 → 传个文件 → 再问」是自然用法，不该逼用户先随便发一句话 |
| 幂等重试 | `clientRequestId` 同理，重试不能产生第二轮对话 |

代价是:**这是一个客户端可控的主键**,而且会被直接用作磁盘目录名。

### 1.2 生命周期

```
前端 newConversation()
  └── genId() 产生 UUIDv4 → conversationId（仅本地，库中不存在）
        │
        ├── 用户先传附件 ──→ POST /ai/chat/workspace/{id}/upload
        │                      └── requireOrCreate → 建行（属主 = 当前用户）
        │
        └── 用户发首轮消息 ─→ POST /ai/chat/run
                               └── ensureOwnedSession → requireOrCreate → 建行
                                     └── 前端 markSessionPersisted() → 放行后续按 id 的查询
```

关键点:`currentSessionId` 非空 **不等于** 会话已落库。首轮发送前它只是个本地占位。
前端用 `sessionPersisted` 这个独立标志区分两者 —— 任何「按 sessionId 打后端」的副作用都必须等它为真。

### 1.3 sessionId 的四个消费点

| 消费点 | 用途 | 风险 |
| --- | --- | --- |
| `ai_chat_session.session_id` | 主键 | 客户端可控主键、抢注 |
| `WorkspaceSandbox.resolveRoot` | 工作区目录名 | 路径穿越 |
| `ContextFileStore.sessionDir` | 上下文文件目录名 | 路径穿越 |
| `ChatSubscriptionRegistry.watchSession` | 事件订阅键 | 未落库时无法比对属主 |

### 1.4 安全模型:sessionId 不只是标识符

绝大多数路径上,越权由**属主比对**兜底 —— 查库拿到 `user_id`,和当前用户比。
但有一条路径比不了:**会话尚未落库时的事件预订阅**。库里没有这一行,无从得知属主,
所以 `SessionAccessGuard.requireOwnedIfExists` 在「不存在」时放行。

这条口子的安全性**完全依赖 id 不可预测**。也就是说,在这个系统里 `sessionId` 同时是标识符
和一个弱能力凭据(capability)。**这是理解本文所有约束的关键。**

口子的泄露面是受限的:session 级订阅只推送 `LIFECYCLE_TYPES`(`run_status`/`done`/`error`/
`cancelled`/`interrupted`)这类元数据,事件正文要另按 `runId` 订阅,那里有独立的属主校验
(`ChatRunService.get`)。所以即便猜中 id,拿到的也只是「这个会话有活动」,不是对话内容。

## 二、本轮修复了什么

### 2.1 安全

| # | 问题 | 影响 | 修法 |
| --- | --- | --- | --- |
| 1 | `SAFE_ID` 允许 `{1,64}`，后端接受 `sessionId=a` | id 可枚举 → 1.4 那层兜底被击穿；他人可抢注短 id 占位 | 新建会话要求 ≥32 位(`SessionIds.requireStrongForNew`)。**只约束新建**，存量短 id 会话继续可用 |
| 2 | 前端弱随机降级 `Math.random()` | 非 HTTPS 部署下 `crypto.randomUUID` 不存在，降级成常态，id 可预测 | 改用 `crypto.getRandomValues` 手工拼 UUIDv4（它不受安全上下文限制，强度与 `randomUUID` 一致）；两者都拿不到时抛错，不生成不安全的 id |
| 3 | `ContextFileStore.sessionDir()` 直接 `resolve(sessionId)`，无任何校验 | 当前不可达(上游都校验了)，但纯靠调用方自觉，新增一个调用方就是穿越点 | 在拼路径处校验 + normalize 后复核未逃出 `contextRoot` |
| 4 | 「会话不存在」与「无权访问」错误消息不同 | 存在性预言机：任何登录用户可探测某 id 是否存在 | 对外统一为「会话不存在或无权访问」；真实原因 + 尝试者 userId 写 warn 日志（越权尝试反而变得可审计） |
| 5 | 工作区建行用普通 `insert` | 并发上传主键冲突 | 统一走 `insert ignore` + **重读再判属主**（见下方警告） |

> **`insert ignore` 的陷阱**:id 已被他人占用时它是**静默 no-op**,不抛主键冲突。
> 若不重新读一次就直接用手里的对象,等于把别人的会话当成自己的。
> `SessionAccessGuard.requireOrCreate` 里那次重读是安全关键,不能优化掉 ——
> `SessionAccessGuardTest.抢注他人id时insert被忽略且重读后拒绝` 锁住了这个行为。

### 2.2 可维护性

同一套「查会话 → 判空 → 比对 userId」的逻辑原本在 **4 个类里复制了 10 份**,
各自的错误消息、是否加行锁、是否允许会话不存在都略有差异。收敛为两个新组件:

- **`SessionIds`**(`ruoyi-system/.../ai/session/SessionIds.java`)—— id 格式与强度的唯一权威。
  `WorkspaceSandbox` 原本自带的第二份正则已改为委托它。
- **`SessionAccessGuard`**(同包)—— 全系统唯一的会话鉴权入口。

各 Controller 保留原有私有方法名,方法体改为**薄委托**(调用点一行未动,风险最小),
规则集中在 Guard。顺带删掉重构后不再使用的注入(`aiChatSessionMapper` 等 6 处)。

### 2.3 功能缺陷

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 新建会话时 `user-messages` 必现 500「会话不存在」+ 红色错误条 | `sendMessage` 先 `markSessionCreated()` 顶上占位 id，`watch(currentSessionId)` 立刻拿它去查，而后端此时还没建行 | 改 `watch([currentSessionId, sessionPersisted])`，落库确认后才拉 |
| 新会话整个生命周期右侧音轨为空，切走再切回才有 | 同上：唯一那次拉取注定失败，且没有重试 | 首轮发送成功后显式 `refreshUserMessages()` |
| 新会话不会出现在左侧列表 | `sessions` 是 ref，`sessions.some(...)` 抛 TypeError（漏了 `.value`），补列表的分支从未执行 | 修正为 `sessions.value.some(...)` |

## 三、架构决策:为什么保留「客户端生成 id」

考虑过改成服务端预分配(`POST /session/draft` 返回 id),它能彻底消除客户端可控主键,
并且可以删掉 `requireOwnedIfExists` 这个特例 —— 鉴权模型会简化成一条规则。

**当前不做**,理由:

1. 收益主要在「id 不可预测」这一点上,而它已由 `SessionIds.requireStrongForNew` + 前端强随机保证;
2. 成本不小:新增往返、需要处理「点了新建但没发消息」产生的空会话行(要么定时清理,要么列表过滤),
   前端新建流程要改成异步;
3. 泄露面本就受限(见 1.4),不值得为此重构核心链路。

**什么时候应该升级到服务端预分配** —— 出现以下任一情况:

- session 级订阅需要推送**事件正文**(而不只是生命周期元数据)。此时 1.4 的口子从元数据泄露
  变成内容泄露,「猜不到 id」这层兜底不够了;
- 出现无法保证 id 强度的第三方客户端(后端拦得住格式但拦不住实现质量);
- 需要「会话链接分享」类功能 —— 那时 sessionId 会变成真正的能力凭据,必须签名而非裸传。

## 四、新增接口规约(**改动前必读**)

任何接受 `sessionId` 的新接口,**不要自己写属主校验**,按下表选一个 Guard 方法:

| 接口性质 | 调用 | 说明 |
| --- | --- | --- |
| 只读(时间线/消息/追踪/工作区浏览) | `requireOwned(id, userId, admin)` | 会话必须存在且属己 |
| 写(删除/清空/回滚) | `requireOwnedForUpdate(...)` + `requireNoActiveRun(id)` | 加行锁，与建行竞态互斥 |
| 可能需要建行(首轮发送/上传) | `requireOrCreate(...)` | 新建分支自动要求 id 强度 |
| 未落库也要放行(**仅事件预订阅**) | `requireOwnedIfExists(...)` | 用前先读 1.4；泄露面必须限于元数据 |
| 按 runId 鉴权 | `requireOwnedRun(run, userId, admin)` | |

补充约束:

1. **身份显式传参**,不要在 Guard 内部读 `SecurityUtils`。WebSocket 消息处理跑在独立线程池上,
   `SecurityContextHolder` 里没有认证信息,身份是握手阶段存进 session attributes 再往下传的。
   隐式取当前用户会在 WS 路径上静默取到 `null`。
   - Controller 传 `getUserId(), SecurityUtils.isAdmin(getUserId())`
   - WS / Service 传 command 里带下来的 `userId, admin`
2. **拿 sessionId 拼任何文件路径前**,先过 `SessionIds.isWellFormed`,并在 normalize 后复核未越界。
   已有两处消费点(`WorkspaceSandbox`、`ContextFileStore`)已内建此检查,新增消费点必须照做。
3. **不要新增第三份 id 正则**。格式规则只有 `SessionIds` 一处。
4. **不要在错误消息里区分「不存在」与「无权」**,那会重新引入存在性预言机。

前端侧:

5. 任何按 `sessionId` 打后端的副作用,判断条件是 `sessionPersisted`,**不是** `currentSessionId` 非空。
6. 新的会话创建入口必须用密码学强随机生成 id,长度 ≥32。

## 五、后续路线

**P1 — 建议近期做**

- [ ] 会话创建限流。目前每次 `POST /ai/chat/run` 都会 `insert ignore` 一行,无速率限制,
      可被刷表。与 client-generated id 无关,任何 create 接口都有,但会话表增长最快。
- [x] 桌面端 `useSessions.js` 的 `genId()` 用 `crypto.randomUUID()` 生成 ≥32 的 sessionId。管理端聊天页同类约定,**尚未抽成共享包**。

**P2 — 触发式,满足第三节任一条件时启动**

- [ ] 服务端预分配 sessionId,取消 `requireOwnedIfExists` 特例。

**已评估、明确不做**

- 把 sessionId 改成签名 token:当前泄露面不值得引入签名与密钥轮换的复杂度。
- 追溯收紧存量短 id:会打死历史会话,收益为零(存量 id 已固化在库和磁盘上)。

- 后端 `mvn test`:346 通过(新增 20:`SessionIdsTest` 8 + `SessionAccessGuardTest` 12)
- 前端 `vite build --mode staging`:通过

**上线前建议手工回归**(涉及会话创建链路,自动化测试覆盖不到 UI 流)

1. 新建会话 → 发首轮 → 确认**无红色错误条**、会话出现在左侧列表、右侧音轨立即有一个刻度
2. 新建会话 → **先传附件再发消息** → 确认会话正常建立、工作区可见
3. 切换历史会话 → 音轨、时间线正常
4. 多标签页开同一会话 → 一端发消息,另一端能同步(验证预订阅未被破坏)
5. 用 A 账号的 sessionId 在 B 账号下请求任一会话接口 → 应返回「会话不存在或无权访问」,
   且服务端 warn 日志有记录

**存量数据**

不需要迁移。收紧只作用于**新建**分支:

- 存量会话(含 32 位无连字符的 job 会话、以及任何历史短 id)读写不受影响;
- 唯一的行为变化:若库里存在 id 短于 32 位的会话,**且**该会话此前从未落库过而现在要新建 ——
  这种情况不存在(能查到就是已落库,走已存在分支)。

**回滚**

改动集中在两个新增类 + 若干薄委托,无数据库变更、无接口契约变更,直接 revert 即可。
