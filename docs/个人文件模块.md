# 个人文件模块设计文档

> 范围:`ObjectStorage` 契约(ai-contract)+ `S3ObjectStorageAdapter`(ruoyi-adapter)+ `AiUserFileServiceImpl` / `AiUserFileProperties`(ruoyi-system)+ `AiUserFileController`(ruoyi-admin)+ 表 `ai_user_file`。前端 `desktop/src/views/FilesView.vue` + `desktop/src/api/userFile.js`。配置 `ruoyi.ai.storage.*` 与 `ruoyi.ai.user-file.*`。

---

## 1. 模块概述

desktop 侧栏「文件」菜单的后端。给每个用户一块**跟人走**的私有文件空间,正文存在 S3 兼容对象存储(MinIO / 阿里云 OSS / 腾讯云 COS / Cloudflare R2),库里只留元数据。

平台此前有四条互不相干的文件落盘路径,本模块是第五条,**刻意不与前四条合并**:

| 用途 | 存储 | 生命周期 | 谁在读写 |
|------|------|----------|----------|
| **个人文件(本模块)** | **S3 兼容对象存储** | **跟用户走** | **用户;投递后模型间接读到副本** |
| 会话工作区沙箱 | 本地磁盘 `ruoyi.ai.tool.workspace-root` | 随会话/项目删除而级联清空 | 用户上传 + 模型 `read`/`write`/`bash` |
| 技能附件 | 本地磁盘 `ruoyi.ai.tool.skill-root` | 跟技能走 | 管理员上传,`loadSkill` 拷副本 |
| 知识库原文 | 本地磁盘 `{ruoyi.profile}/kb/{kbId}` | 跟知识库文档走 | 摄入管线 |
| RuoYi 原生上传 | 本地磁盘 `{ruoyi.profile}/{avatar,upload}` | 跟业务实体走 | 若依原生 |

### 1.1 为什么不把会话工作区也搬到对象存储

**这是本模块最重要的边界,改代码前必须理解。**

会话工作区上跑的是真实进程:`ShellTool` 用 `ProcessBuilder` 执行 `bash`,`FileTools` 有 26 处直接 `java.nio.Files.*`(`read`/`write`/`edit`/`grep`/`find`/`ls`)。对象存储没有 POSIX 语义 —— 没有真目录、不能 seek 写、进程 cd 不进去。把工作区搬上去等于放弃 shell 与文件工具能力。

因此两者之间只能**拷贝**,不能共享。拷贝不是妥协,是唯一能同时保住两边语义的做法。

两个方向各有一个接口:

| 方向 | 接口 | 用途 | 前端入口 |
|---|---|---|---|
| 工作区 → 个人空间 | `POST /ai/files/save-from-workspace` | AI 在工作区产出的东西收进个人空间长期保存 —— 工作区随会话删除而清空,存进来才留得住 | 工作区抽屉每个文件行的「存到文件」 |

> **反馈为什么做在按钮上而不是只发 toast**:全局 toast 固定在页面顶部居中(`.toasts` 是 `top:16px; left:50%`),而工作区抽屉贴在最右侧 —— 实测点保存时 toast 出现在 x≈523,按钮在 x≈1213,隔了大半屏,视线在右边根本扫不到。所以按钮本身有三态(默认箭头 / 保存中转圈 / 已保存绿勾),绿勾常驻且禁用,顺带挡住重复点击造成的重复记录;`loadTree` 时清空标记,因为目录内容可能已变。toast 仍然保留,给的是文件名这类细节。
| 个人空间 → 工作区 | `POST /ai/files/{id}/attach` | 把个人文件拷进会话 `uploads/`,模型即可 `read` | **当前未暴露**(接口与测试保留) |

两个方向共用 `AiUserFileServiceImpl#persist`:限额校验 → 秒传判定 → 写对象 → 落库,所以配额、单文件上限、秒传对两个入口一视同仁。`saveFromWorkspace` 额外走 `WorkspaceSandbox.resolveSafe` 做路径穿越防护 —— `path` 由前端传入,不能让它捞到沙箱外的文件。

## 2. 分层与依赖方向

```
ai-contract      ObjectStorage / StoredObject / ObjectWriteRequest / ObjectReadHandle
                 —— 纯接口,只依赖 jackson,不知道 S3 存在
      ↑
ruoyi-system     AiUserFileServiceImpl(业务规则)+ AiUserFileProperties(配额)
                 + AiUserFile / AiUserFileMapper(域与持久化)
                 —— 面向 ObjectStorage 接口编程,编译期不碰 AWS SDK
      ↑
ruoyi-adapter    S3ObjectStorageAdapter + ObjectStorageProperties + ObjectStorageConfig
                 —— AWS SDK v2 只出现在这一层
      ↑
ruoyi-admin      AiUserFileController(/ai/files)
```

依赖方向与仓库既有的 `WorkspaceStorage` / `LocalWorkspaceStorageAdapter` 完全一致,零循环。

### 2.1 为什么不复用 `WorkspaceStorage`

`ai-contract` 里已有一个 `WorkspaceStorage`(`stat`/`open`/`write`,配 `WorkspaceRef` + 相对 path + etag CAS)。两者刻意不合并:

- `WorkspaceStorage` 是**工作区**语义:相对路径、目录树、etag 乐观锁,底下必须是 POSIX 文件系统。
- `ObjectStorage` 是**对象**语义:扁平 key、预签名 URL,底下是 S3,没有目录也不能原地改。

合并的结果是两边都退化:要么给对象存储强加它做不到的 POSIX 承诺,要么把工作区的目录语义压扁。

> 注:`WorkspaceStorage` 目前仍是**未接线的骨架** —— 全仓只有接口、`LocalWorkspaceStorageAdapter` 和一个单测,没有生产消费方。本模块没有改变这一点。

## 3. 关键类与职责

### 3.1 `ObjectStorage`(ai-contract)

五个方法:`put` / `open` / `stat` / `delete` / `presignedUrl`,外加三个 default 便捷重载。

**接口里没有 bucket 参数** —— 桶是部署期配置,由实现方持有,调用方只认 key。

`ObjectWriteRequest.size` 必须准确:S3 单次 PUT 需要预先声明 Content-Length,传 -1 会退化成把整个流读进内存算长度,大文件直接打爆堆。

### 3.2 `S3ObjectStorageAdapter`(ruoyi-adapter)

用**同步** `S3Client` + `ApacheHttpClient`,排除了 `netty-nio-client`。原因:调用方是 Servlet 线程上的上传下载,拿异步 Future 后还是要阻塞等;而 `S3AsyncClient` 会把 netty 拉进依赖树,与 Spring AI 用的 reactor-netty 版本对齐是额外负担。

| 细节 | 位置 | 说明 |
|---|---|---|
| `presigner` 与 `client` 共用配置 | 构造函数 | endpoint / pathStyle 必须一致,否则签出的 URL 主机名形态与实际服务对不上,报 403 SignatureDoesNotMatch |
| `absoluteKey` | 私有方法 | 拼部署级 `keyPrefix`;对外的 key 始终不含前缀,换前缀不用改库 |
| `normalizeEtag` | 私有方法 | S3 的 ETag 带引号,剥掉再存,免得比对时因引号不等误判 |
| `contentDisposition` | 私有方法 | 非 ASCII 文件名走 RFC 5987 `filename*`,否则中文名下载后乱码 |
| `stat` 的 404 兜底 | `catch (S3Exception)` | headObject 对不存在的键返回 404 但不带错误体,部分实现(含 MinIO)抛的是通用 `S3Exception` 而非 `NoSuchKeyException` |

由 `ObjectStorageConfig` 在 `ruoyi.ai.storage.enabled=true` 时构造;**关闭时 bean 不存在**,没配存储的开发机与 CI 不会因此启动失败。开启但漏配必填项时在启动期就报出是哪一项。

### 3.3 `AiUserFileServiceImpl`(ruoyi-system)

用 `ObjectProvider<ObjectStorage>` 注入,取不到就抛「对象存储未配置」的业务提示。

**对象键布局**:`user/{userId}/{yyyyMM}/{uuid}.{ext}`

- 不拿原始文件名做键 —— 中文、空格、`../`、超长名在不同 S3 实现下行为各异,挡在存储层之外;展示名归展示名、键归键。
- 按月分片是为了让存储控制台还能按目录浏览,单前缀几十万对象翻不动。
- 扩展名只保留字母数字、截到 16 字符,它只影响控制台可读性,不参与任何判断。

**秒传**:同一用户上传相同 SHA-256 的内容时复用对象,只新增一条元数据记录。**跨用户不复用** —— 对象键里带 userId,共用会让「A 删了文件 B 还看得见」变成需要全局引用计数才能解释清楚的问题,省下的空间不值这个复杂度。

**删除**:软删元数据,再按 `countLiveByObjectKey` 判断对象本体能否真删(秒传让多条记录可能共用一个对象)。存储侧删除失败只记 warn 不回滚 —— 元数据已软删,留下的孤儿对象不可达,可容忍。

**配额**:按存活记录 `sum(file_size)`。秒传的每条记录**各自计入** —— 用户看到几个文件就该算几份,物理去重是实现细节,不该影响他对「我用了多少」的判断。

### 3.4 查询实体的字段不能叫 `orderBy`(踩过的坑)

`AiUserFile` 的排序字段叫 `sortMode` 而不是 `orderBy`,这是**被线上 500 打出来的**:

`application.yml` 里 `pagehelper.supportMethodsArguments: true`,PageHelper 在这个开关下会**反射读取 Mapper 方法参数对象里名为 `orderBy` 的属性**,直接拼成 `order by ${orderBy}`。结果是 Mapper XML 里的 `<choose>` 白名单被整个绕过:

```
### SQL: SELECT ... FROM ai_user_file WHERE del_flag = '0' AND user_id = ? order by date
### Cause: Unknown column 'date' in 'order clause'
```

`date` 正是传进去的排序模式值。这不只是个 500 —— 它等于把用户可控字符串送进了 SQL 拼接路径(本模块的 `normalizeOrderBy` 白名单挡住了实际注入,但不该依赖这一层)。

**新增任何带排序参数的查询实体时都要避开 `orderBy` 这个名字**。`AiUserFileServiceTest.entity_hasNoOrderByProperty_pageHelperWouldHijackIt` 用反射钉住了这一点。

### 3.5 归属校验

每个 Service 方法都以 `userId` 开头,校验一律下沉到 SQL 的 `where` 条件(`selectByIdAndUser`、`softDeleteByIdAndUser` 都带 `user_id`)。越权读写这类问题靠「Service 记得传条件」是守不住的,做进 Mapper 方法签名才是。

Controller **没有 `@PreAuthorize`**:这是 C 端用户操作自己的文件,不是后台管理的权限点。

## 4. 数据表 `ai_user_file`

见 `sql/ai_user_file.sql`(增量)与 `sql/init/13_ai_user_file.sql`(建库)。

| 字段 | 说明 |
|---|---|
| `user_id` | 强制非空,不允许无主文件 |
| `object_key` | 不含部署级 keyPrefix |
| `content_hash` | SHA-256,秒传用 |
| `del_flag` | 软删 |

三条索引:
- `idx_user_file_owner (user_id, del_flag, create_time)` —— 列表页固定按此过滤+排序,联合索引可覆盖排序避免 filesort
- `idx_user_file_hash (user_id, content_hash)` —— 秒传查重。**刻意不做唯一约束**:软删的行 `content_hash` 仍在,唯一键会导致「删掉再传同一个文件」撞键失败
- `idx_user_file_object (object_key)` —— 删除时反查引用计数

## 5. HTTP API `/ai/files`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/ai/files` | 列表。`keyword` / `orderBy`(date/name/size)。返回含 `storageEnabled` |
| GET | `/ai/files/quota` | 已用 / 配额 / 条数 / 单文件上限 |
| POST | `/ai/files/upload` | 上传,`multipart` 字段名 `file` |
| GET | `/ai/files/{fileId}/download` | 后端转发下载,带鉴权 |
| GET | `/ai/files/{fileId}/preview-url` | 预签名直链;`download=true` 则带另存为头 |
| PUT | `/ai/files/{fileId}/name` | 重命名(只改展示名,object_key 不动) |
| DELETE | `/ai/files/{fileId}` | 软删 + 无其他引用时删对象 |
| POST | `/ai/files/save-from-workspace` | **工作区文件 → 个人空间**,前端入口在工作区抽屉每个文件行 |
| POST | `/ai/files/{fileId}/attach` | 个人文件 → 工作区副本。接口保留,当前前端未暴露入口 |

**`objectKey` 不出网**:它是存储内部布局,泄露等于公开桶结构;前端拿 `fileId` 就够办所有事。

**下载走后端转发、预览走预签名**:下载要鉴权且量小;而每张缩略图都走转发等于各占一个 Servlet 线程,所以图片预览让浏览器直连存储。文本预览仍走后端 blob —— 预览要读取内容,跨域直取会被 CORS 挡住,后端转发天然同源。

## 6. 配置

`application-ai.yml`,两段分开是刻意的 —— 换存储厂商不该顺带改配额:

```yaml
ruoyi:
  ai:
    storage:          # 怎么连存储(ObjectStorageProperties,ruoyi-adapter)
      enabled: false
      endpoint / region / access-key / secret-key / bucket
      path-style-access / key-prefix
    user-file:        # 业务规则(AiUserFileProperties,ruoyi-system)
      user-quota-bytes / max-file-bytes / max-files-per-user / presign-ttl-seconds
```

四类服务的差异只在 `endpoint` / `region` / `path-style-access`:

| 服务 | endpoint | region | path-style-access |
|---|---|---|---|
| MinIO | `http://127.0.0.1:9000` | `us-east-1` | **true** |
| 阿里云 OSS | `https://oss-cn-hangzhou.aliyuncs.com` | `oss-cn-hangzhou` | false |
| 腾讯云 COS | `https://cos.ap-guangzhou.myqcloud.com` | `ap-guangzhou` | false |
| Cloudflare R2 | `https://{account}.r2.cloudflarestorage.com` | `auto` | **true** |

> `path-style-access` 设错的症状是 **404 或 SignatureDoesNotMatch,而不是连不上**,排查时容易被误导。

`max-file-bytes` 必须 ≤ `spring.servlet.multipart.max-file-size`(当前 50MB),否则超限请求会被 Tomcat 在进 controller 之前拒掉,用户看到的是 500 而不是友好提示。

## 7. 前端

### 7.0 前后端交互

**C 端(desktop 侧栏「文件」)**:`desktop/src/views/FilesView.vue` + `desktop/src/api/userFile.js`,调用 `/ai/files`(`AiUserFileController`)。**管理端(ruoyi-ui)**:`ruoyi-ui/src/views/ai/userfile/index.vue` + `api/ai/userFile.js`,调用 `/ai/userfile`(`AiUserFileAdminController`)。两套刻意分开,鉴权与可见范围不同(见 §8.1)。

| 前端操作 | API 函数 | HTTP | 后端端点 |
| --- | --- | --- | --- |
| 列表/配额 | `listUserFiles` / `getUserFileQuota` | GET | `/ai/files` / `/ai/files/quota` |
| 上传(串行) | `uploadUserFile(file, onProgress)` | POST | `/ai/files/upload` |
| 预览直链 | `getUserFilePreviewUrl(fileId)` | GET | `/ai/files/{fileId}/preview-url` |
| 下载 | `downloadUserFileBlob(fileId, filename)` | GET | `/ai/files/{fileId}/download` |
| 重命名/删除 | `renameUserFile` / `deleteUserFile` | PUT/DELETE | `/ai/files/{fileId}/name` / `/ai/files/{fileId}` |
| 挂到会话 | `attachUserFileToSession(fileId, sessionId, projectId)` | POST | `/ai/files/{fileId}/attach` |
| 工作区存回个人文件 | `saveWorkspaceFileToUserFiles(...)` | POST | `/ai/files/save-from-workspace` |
| 管理端列表/总量/用量/删除 | `listUserFile` / `getUserFileTotals` / `getUserFileUsage` / `delUserFile` | GET/DELETE | `/ai/userfile...` |

**交互要点**:
- **上传串行 + 进度回调**:`uploadUserFile(file, onProgress)` 用 XMLHttpRequest 报进度,顶栏按钮与整页拖拽都走同一函数;刻意不并发(多文件并行会抢带宽且进度不可读)。
- **预览走预签名直链**:`getUserFilePreviewUrl` 返回 S3 预签名 URL,图片 `UserFilePreviewModal` 直接 `<img src>` 展示;文本类则拉 blob。不经过后端二次转发。
- **过滤与排序在前端**:单用户 ≤2000 条元数据一次拉全量本地过滤;后端同样支持 `keyword`/`orderBy`,数据量大时可切回后端过滤。
- **挂到会话是桥接动作**:`attachUserFileToSession` 把个人文件复制进会话工作区,后续模型才读得到副本 —— 个人文件本体不直接进上下文。
- 管理端列表可见全用户,按钮权限 `ai:userfile:list` / `:remove` 门控,与 C 端"焊死 userId"形成对照(见 §8.1)。

### 7.1 视觉对齐

- 列表 / 配额来自 `/ai/files` 与 `/ai/files/quota`
- 上传:顶栏按钮 + 整页拖拽投放,**串行**上传(并行发多个大文件会互相抢带宽,进度条也给不出有意义的数字)
- 预览:独立组件 `UserFilePreviewModal`,图片走预签名直链、文本走 blob
- 行内操作:预览 / 下载 / 重命名 / 删除

### 7.1 视觉对齐

第一版是在旧 UI 壳上打补丁,与 KbView / ResourceView 明显不一致,已重做:

| 项 | 重做前 | 现在(对齐 KbView) |
|---|---|---|
| 图标 | 6 处 emoji `📁🖼️📄💻📦` | `utils/fileKind.js` 的线性 SVG,24 viewBox / 1.8 描边 / round 端点,按类型区分 |
| 头部 | 56px 条 + 页面级主题切换按钮 | 大标题 + 副标题;主题切换属于全局设置,正式入口在 SettingsModal |
| 布局 | 340px 侧栏 + 右侧预览分栏 | 单栏列表 + 弹窗预览 |
| 行内操作 | 纯图标按钮 | 图标 + 文字,同 `document-row__actions` |
| 加载态 | 纯文字 | `<AppPageLoader compact />` |

`utils/fileKind.js` 同时被列表和预览弹窗使用,图标与「能否文本预览」的判定只有一处。

## 8. 后台管理端

`ruoyi-ui` 侧,菜单挂在 2110「能力」下(与知识库管理、长期记忆同级)。

| 组成 | 位置 |
|---|---|
| Controller | `AiUserFileAdminController`,前缀 `/ai/userfile` |
| Service | `IAiUserFileAdminService` / `AiUserFileAdminServiceImpl` |
| Mapper | `selectAdminList` / `selectAdminByIds` / `softDeleteByIds` / `selectAdminUsageByUser` / `selectAdminTotals` |
| 页面 | `ruoyi-ui/src/views/ai/userfile/index.vue` |
| API | `ruoyi-ui/src/api/ai/userFile.js` |
| 菜单 | `sql/ai_user_file_menu.sql`(menu_id 2130-2132) |

### 8.1 为什么与 C 端分成两套

`/ai/files`(C 端,desktop 用)与 `/ai/userfile`(管理端)刻意不合并:

| | `/ai/files` | `/ai/userfile` |
|---|---|---|
| 鉴权 | 无 `@PreAuthorize`,登录即可 | `ai:userfile:list` / `:remove` |
| 可见范围 | 只有自己 —— 归属焊在 SQL 的 `where user_id = ?` 里 | 跨用户 |
| Mapper 方法 | 每个都强制带 `userId` 入参 | `admin` 前缀,不带 userId 约束 |

Mapper 方法用 `admin` 前缀命名,是为了让「这个查询能看到别人的数据」在调用点一眼可见;塞进同一个 Controller 加 boolean 开关的话,可见范围就变成运行时判断了。

### 8.2 功能范围

**只读监控 + 删除**,不含按用户配额:

- 汇总卡片:文件总数 / 占用空间 / 使用人数 / 单用户配额
- 文件明细:按 userId、用户名、文件名、MIME 大类筛选,分页,单条与批量删除
- 按用户统计:占用倒序,配额使用率进度条,可跳转到该用户的明细

**配额目前是全局配置**(`ruoyi.ai.user-file.user-quota-bytes`),不是按用户存的。管理端的「配额使用率」拿它做分母。要支持给单个用户调配额,得先改数据模型(加配额字段或表),不只是加页面。

### 8.3 删除的顺序

与 C 端一致:先软删台账、再清理无引用的对象。存储侧失败只记 warn 不回滚 —— 用户可见的删除已经生效,留下的孤儿对象不可达,可容忍;反过来先删对象则可能出现「台账还在但正文没了」。

秒传让多条记录可能共用一个 `object_key`,所以逐个复查 `countLiveByObjectKey`,不能拿到 key 就删。对象存储未配置时仍然软删台账 —— 否则管理员连记录都清不掉。

> 管理端列表直接返回实体(含 `object_key`),与 C 端 `toView()` 剥掉它的做法不同。这是有意的:管理员排障时需要拿 key 去存储控制台对照。

## 9. 已知约束

- **多实例**:个人文件本身在对象存储上,天然跨节点共享;但 `/attach` 的落点是会话工作区,仍受 `workspace-root` 必须指向共享持久卷这一既有约束。
- **孤儿对象**:删除时存储侧失败会留下不可达对象,当前没有对账任务清理。
- **`ai_user_file` 无目录层级**:UI 是扁平列表 + 搜索,库里也没有 folder 字段。要加目录需同时改表、Mapper 与 UI。
- **秒传只在同用户内生效**,跨用户相同内容会各存一份。
- **没有断点续传/分片上传**:单文件上限 50MB,单次 PUT 足够;更大的文件需要引入 multipart upload。
